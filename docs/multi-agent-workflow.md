# Мультиагентный workflow для миграции

Непрерывный, **полностью автономный** пайплайн исполнения [`docs/implementation/`](implementation/) (Фаза 9, все подфазы 9.1–9.5 подряд, без участия пользователя): один агент реализует задачу, второй проверяет качество (включая браузерное тестирование для UI-задач), третий делает ревью кода. Внутри одной фазы это повторяется для каждой задачи; когда все задачи фазы выполнены — отдельный **фазовый контроль** (§5а) перепроверяет фазу целиком, и при успехе пайплайн сам коммитит изменения и переходит к следующей фазе.

**Статус:** предложено (ожидает утверждения)

Связанные документы:

- [`implementation/`](implementation/) — файлы фаз, единственный durable-трекер прогресса (агенты редактируют поля `Статус`/`Попытки`/`Заметки агентов` прямо в файлах — см. [`implementation/README.md`](implementation/README.md) за форматом)
- [`coding-conventions.md`](coding-conventions.md) §6 — политика коммитов (эта фаза — явно авторизованное пользователем исключение из общего правила "коммит только по запросу")
- [`specs/nextjs-migration-spec.md`](specs/nextjs-migration-spec.md) и [`specs/static-prototype-spec.md`](specs/static-prototype-spec.md) §5.1/§4 — эталон архитектуры и UI, с которым сверяется браузерное тестирование
- [`contracts/content-data-contract.md`](contracts/content-data-contract.md) и [`contracts/image-generator-api-contract.md`](contracts/image-generator-api-contract.md) — формальные DoD-критерии для соответствующих задач
- [`ADRs/adr-001-cursor-rules-delivery.md`](ADRs/adr-001-cursor-rules-delivery.md) — происхождение процессных правил (verify→review, ревью в отдельном контексте)

## 1. Цель и принципы

- **Полная автономность выполнения, без участия пользователя между фазами и задачами.** Пользователь запускает пайплайн один раз; дальше он сам проходит все задачи всех подфаз 9.1–9.5 и сам коммитит после каждой фазы — это явное решение пользователя, зафиксированное здесь (2026-08-21), а не default-поведение Claude Code. **Push в удалённый репозиторий пайплайн не выполняет никогда** — это единственная вручную выполняемая пользователем часть workflow (см. §9).
- **Последовательный пайплайн на задачу и на фазу, не параллельный fan-out воркеров.** Anthropic ("Building Effective Agents", "How we built our multi-agent research system") отмечает, что кодинг-задачи хуже подходят для параллельного распараллеливания воркеров, чем research-задачи — меньше независимо параллелизуемых подзадач, больше разделяемого контекста между шагами, выше риск накопления ошибок при автономных цепочках. Здесь и задачи внутри фазы, и сами фазы обрабатываются строго последовательно.
- **Writer/Reviewer-разделение контекста.** Проверяющие стадии (quality-check, code-review — как на уровне задачи, так и на уровне фазы, §5а) выполняются **свежим** сабагентом, не видящим рассуждений `implementer`'а — только итоговый diff и критерии приёмки. Это снимает bias самооценки.
- **Машинно проверяемый Definition of Done обязателен** — и на уровне задачи, и на уровне фазы (§5а). Без него цикл не может сам себя корректно завершить.
- **Автономность не отменяет безопасные точки остановки.** Пайплайн не пропускает и не форсирует переход при провале — при исчерпании ретраев (на задаче или на фазе) он останавливается и явно эскалирует к человеку (§6). Это единственное условие, при котором полностью автономный прогон прерывается сам.

## 2. Пайплайн — общая схема

```
Фаза N:
  ┌─ для каждой задачи фазы (по порядку) ──────────────────────────────┐
  │  Implement → Quality-check → Code-review                            │
  │       │             │              │                                │
  │       └── провал ───┴──────────────┴──→ retry (≤3) → снова Implement │
  │                                              │                       │
  │                                        3 провала подряд              │
  │                                              ↓                       │
  │                                    STOP + эскалация (Статус: blocked)│
  └─ все задачи фазы done ───────────────────────────────────────────────┘
                    │
                    ▼
        Фазовый контроль (§5а): quality-checker + code-reviewer
        над ВСЕЙ фазой целиком (не последней задачей)
                    │
        ┌───────────┴───────────┐
     успех                   провал
        │                       │
        ▼                 retry (≤3 фазовых попытки) → откат проблемных задач
   git commit                   │
   (см. §5а)              исчерпаны попытки
        │                       ↓
        ▼                 STOP + эскалация (Статус фазы: blocked)
  Статус фазы: done
        │
        ▼
  автопереход к первой задаче следующей фазы
  (без подтверждения пользователя)
```

- **Вход** каждой задачи — один подраздел `### 9.N.M` со `Статус: todo` из текущего файла фазы в `docs/implementation/` + привязанный к нему Definition of Done.
- **Implement** — ведущая сессия выставляет `Статус: in-progress`, затем `implementer` реализует ровно одну задачу; сам не редактирует статус (см. `.claude/commands/next-task.md`).
- **Quality-check** / **Code-review** — как описано в §3–4, свежий контекст, не правят код.
- Когда **все** задачи текущего файла фазы получили `Статус: done` — пайплайн **не** коммитит и не переходит к следующей фазе сразу, а запускает фазовый контроль (§5а).

## 3. Роли и расположение

| Роль | Файл | Доступ |
|---|---|---|
| `implementer` | `.claude/agents/implementer.md` | Read/Write/Edit/Bash/Grep/Glob — единственная роль с правом записи |
| `quality-checker` | `.claude/agents/quality-checker.md` | Read/Bash/Grep/Glob (без Edit/Write) + браузерные preview-инструменты (`mcp__Claude_Browser__*`) для UI-задач |
| `code-reviewer` | `.claude/agents/code-reviewer.md` | Read/Grep/Glob/Bash (`git diff` и т.п.) — без Edit/Write; порт `agent-code-review-subagent.mdc` (см. ADR-001 §3) |

Те же `quality-checker` и `code-reviewer` вызываются повторно на фазовом контроле (§5а) — просто с более широкой областью (весь diff фазы, все DoD фазы, а не одной задачи), отдельная 4-я роль не заводится.

Каждый вызов — отдельный сабагент (`subagent_type`), отдельный контекст, не наследует рассуждения предыдущей стадии.

## 4. Definition of Done (уровень задачи)

Каждая задача в `docs/implementation/phase-9.*.md` формулируется так, чтобы иметь привязанную машинную проверку (поле `Definition of Done` в самой задаче):

- **Базовые проверки (все задачи), три отдельные именованные команды — не одна общая «сборка»:**
  1. `npm run typecheck` (`tsc --noEmit`) — 0 ошибок типов.
  2. `npm run lint` (ESLint) — 0 ошибок (warnings не блокируют, если явно не помечены как error).
  3. `npm run build` (`next build`) — завершается без ошибок.
  Плюс: для задач миграции контента — count-parity скрипт (`scripts/migrate-json-to-ts.ts`, 114/16/102/110, см. `contracts/content-data-contract.md` §3); для задач со специфичным файлом — существование файла и наличие ожидаемых экспортов. Все три скрипта (`typecheck`/`lint`/`build`) должны существовать в `package.json` начиная с задачи 9.2.1 (скелет Next.js) — это часть её Definition of Done.

- **Дополнительно для задач, затрагивающих UI** (изменения в `app/**`, `components/**`, стилях, shadcn-примитивах — `quality-checker` определяет это по путям файлов в diff):

  1. **Браузерное тестирование** — `preview_start`/`navigate` на затронутый маршрут, `read_console_messages` (0 ошибок), `read_page` (структура по §7.3 `specs/static-prototype-spec.md`), `resize_window` на `mobile`/`tablet`/`desktop` (брейкпоинты §4), для drawer/навигации — `aria-expanded`/`aria-controls`/`aria-current`/фокус-трап, `computer` (screenshot) как доказательство.
  2. **Визуальная консистентность** — только цвета `--md-sys-color-*`/переопределённых shadcn-токенов (§5.1 `specs/static-prototype-spec.md`), без AI-slop-паттернов из `CLAUDE.md`.
  3. Провал любого пункта 1–2 — провал стадии Quality-check, не "мягкая" рекомендация.

- Итог стадии — структурированный pass/fail с причиной, дописывается в `Заметки агентов` задачи.

## 5. Механизм продвижения (уровень задачи)

1. **Хуки `SubagentStop`/`Stop` внутри одной задачи.** `SubagentStop`, отфильтрованный по `agent_type`, — примитив авто-триггера следующей стадии. `Stop` — точка, где решается: `Статус: done` и следующая задача, или retry/эскалация.
2. **`/loop` как внешний драйвер** — между задачами и **между фазами**. Таргет-промпт — `.claude/commands/next-task.md`: находит первую задачу со `Статус: todo` в файлах фаз по порядку (`phase-9.1` … `phase-9.5`); если в текущей фазе задач больше нет, но фаза ещё не прошла фазовый контроль — запускает §5а; если фаза `done` — переходит к следующему файлу фазы автоматически, без подтверждения пользователя.
3. **Почему не Agent Teams** — Agent Teams рассчитан на координацию параллельных сессий; здесь всё строго последовательно (одна задача/фаза за раз), дополнительная координация не окупается.

## 5а. Фазовый контроль и коммит

Запускается один раз на фазу, когда **все** задачи её файла получили `Статус: done`. Отдельный, более широкий прогон, а не повтор последней задачи:

1. **`quality-checker` (широкая область)** — повторно проверяет **все** Definition of Done фазы целиком (не только последней задачи). **Обязательно, с нуля, для всей фазы** (не переиспользовать результат последней задачи):
   1. `npm run typecheck` — 0 ошибок.
   2. `npm run lint` — 0 ошибок.
   3. `npm run build` — без ошибок.
   Плюс: полный count-parity (для 9.1), для фаз с UI — регрессионный браузерный обход **всех** маршрутов/компонентов, затронутых фазой (не одного), чтобы поймать взаимные регрессии между задачами фазы. Провал любой из трёх команд — провал фазового контроля целиком, даже если каждая задача по отдельности проходила эти же проверки раньше (интеграционные регрессии между задачами одной фазы — именно то, что должен ловить этот повторный прогон).
2. **`code-reviewer` (широкая область)** — ревью **полного** накопленного diff фазы (всё, что изменилось с последнего коммита — так как коммитов внутри фазы нет, это естественно весь diff фазы), не только последней задачи.
3. **Успех обеих проверок** → коммит:
   - `git add` затронутых фазой файлов;
   - `git commit` с сообщением `type(scope): summary` (`scope` = id фазы, например `feat(phase-9.1): контент как TypeScript`, без префикса ветки — см. `coding-conventions.md` §6), с перечислением завершённых задач в теле коммита и стандартным `Co-Authored-By` для коммитов, сделанных Claude Code;
   - `Статус фазы: done` в файле фазы;
   - автоматический переход к первой задаче следующего файла фазы (без остановки, без подтверждения пользователя).
4. **Провал любой из двух проверок** → это отдельный, **фазовый** ретрай-бюджет (до 3 попыток фазового контроля, независимо от бюджета отдельных задач): причина дописывается в `Заметки агентов` конкретной задачи(-ач), которые нужно доработать, их `Статус` возвращается на `in-progress`, и для них повторяется обычный цикл §2 (Implement → Quality-check → Code-review) — не вся фаза переделывается с нуля, только то, что провалило фазовый контроль.
5. **Исчерпаны 3 фазовые попытки** → `Статус фазы: blocked`, коммита нет, пайплайн останавливается и выводит диагностику — как и на уровне задачи (§6), никогда не коммитит частично проверенный результат и не переходит к следующей фазе через голову провала.

**Коммит — единственное автоматическое git-действие пайплайна.** `git push` пайплайн не выполняет ни при каком исходе — это исключительно ручное действие пользователя (см. §9).

## 6. Ретраи и эскалация

- **Уровень задачи:** максимум 3 попытки на задачу (поле `Попытки`). При провале — причина в `Заметки агентов`, feedback в промпт `implementer`'а на следующую попытку. Исчерпаны — `Статус: blocked`, пайплайн останавливается на этой задаче (эскалация — фаза не может пройти фазовый контроль, пока в ней есть `blocked`-задача).
- **Уровень фазы:** максимум 3 попытки фазового контроля (§5а), независимый счётчик. Исчерпаны — `Статус фазы: blocked`, коммита нет, пайплайн останавливается.
- В обоих случаях пайплайн **никогда** не помечает задачу/фазу выполненной при провале и не пропускает её, чтобы продолжить дальше — застрявшая единица блокирует автопродвижение до вмешательства человека.

## 7. Гигиена контекста

- Файлы `docs/implementation/phase-9.*.md` — единственный durable state/progress tracker; при каждом перезапуске (`/loop`) состояние читается заново из полей `Статус`/`Попытки`/`Заметки агентов`.
- Между задачами — свежий контекст на каждый сабагент-вызов плюс `/clear` в ведущей сессии перед следующей задачей.
- Между фазами — то же самое, плюс сделанный коммит (§5а) естественным образом становится границей: фазовый контроль следующей фазы будет ревьюить diff только этой новой фазы (сравнение с последним коммитом), а не всей истории.
- Что переносится: файлы фаз, `coding-conventions.md`, спеки/контракты (статичные референсы). Что не переносится: цепочка рассуждений и промежуточные неудачные diff'ы прошлых задач/фаз (кроме итоговых résumé в `Заметки агентов`).

## 8. Интеграция с `docs/implementation/`

- Файлы фаз — единственный источник истины по прогрессу; никакой отдельный "прогресс-файл" пайплайна не заводится.
- `docs/implementation-checklist.md` (Фазы 0–8) — архив старого статического прототипа, пайплайн его не читает и не редактирует.
- Задачи должны быть атомарными и иметь однозначно проверяемый DoD (§4) — требование к их формулировке, не только к работе пайплайна.

## 9. Ручные точки входа/остановки

- **Старт — единственное ручное действие для запуска.** Пользователь один раз вызывает `.claude/commands/next-task.md` (напрямую или через `/loop`) — дальше пайплайн сам проходит все задачи и все фазы 9.1–9.5 без дополнительных подтверждений.
- **Автоматическая остановка** происходит только в двух случаях: (а) вся Фаза 9 завершена (все 5 файлов фаз `done`), (б) эскалация — задача или фаза `blocked` после исчерпания ретраев (§6). В обоих случаях пайплайн сам останавливает `/loop` и явно сообщает пользователю.
- **Ручная остановка** — пользователь может прервать `/loop` в любой момент.
- **Коммиты — автоматические, по одному на фазу, после успешного фазового контроля (§5а).** Это явное исключение из общего правила Claude Code "коммит только по запросу пользователя", авторизованное пользователем именно для этого пайплайна (см. `coding-conventions.md` §6) — не распространяется ни на какую другую работу в этом репозитории.
- **`git push` — исключительно вручную, пользователем.** Пайплайн не выполняет `push` ни при успехе, ни при эскалации, ни при остановке — это единственный шаг, оставленный пользователю намеренно.

## 10. Открытые вопросы

1. Точная реализация `.claude/commands/next-task.md` — оформлена вместе с `.claude/agents/*.md`, не блокирует принятие этого документа.
2. Формат тела коммита (список задач, ссылка на файл фазы) — фиксируется при первом реальном коммите пайплайна, не блокирует архитектуру.
3. Нужен ли отдельный агрегированный отчёт по прогрессу помимо чтения `Статус`/`Статус фазы` в файлах — не required для MVP, можно добавить позже.
