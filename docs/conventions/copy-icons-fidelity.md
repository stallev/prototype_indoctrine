## 1. Копирайтинг интерфейса

Проект одноязычный (русский), локализация/переключение языка не планируются — полная i18n-инфраструктура (файлы сообщений на несколько языков, provider локали) из референса **не переносится** (см. ADR-001 §4).

Тем не менее, короткие UI-строки чужеродной от контента (не текста вопросов/ответов/стихов из `content/*.ts`, а элементы интерфейса — «Предыдущий», «Следующий», «К разделу», «Скачать», сообщения об ошибке формы генератора) — собрать в одном небольшом модуле `lib/messages.ts`, а не дублировать одну и ту же строку в нескольких компонентах:

```ts
export const messages = {
  nav: { prev: 'Предыдущий', next: 'Следующий', toTopic: 'К разделу' },
  imageGenerator: {
    submit: 'Сгенерировать',
    download: 'Скачать',
    pending: 'Генерация…',
    genericError: 'Не удалось сгенерировать изображение. Попробуйте ещё раз.',
  },
} as const;
```

Тон — без маркетинговых формулировок, в стиле текущего прототипа (см. "Avoid AI slop" в `CLAUDE.md`).

## 2. Иконки

- Для UI-иконок (навигация, кнопки, состояния) — `lucide-react`, стандартный набор shadcn/ui.
- Импортировать конкретные иконки (`import { Menu } from 'lucide-react'`), не namespace-импорт — для tree-shaking.
- Не добавлять кастомный inline SVG для стандартного UI-глиптографа, если подходящая иконка уже есть в Lucide.
- **Не путать с иллюстрациями** — 114 SVG-иллюстраций вопросов (`public/illustrations/`) не являются "иконками" в смысле этого правила и живут по правилам `specs/svg-illustration-spec.md`, не Lucide.

## 3. Визуальное соответствие текущему прототипу

Работающий статический прототип ([`static-prototype-spec.md`](../specs/static-prototype-spec.md), `index.html`+vanilla JS, `npm run serve`) — не просто архитектурный референс, а **визуальный эталон**: при переносе на Next.js/shadcn воспроизводить его внешний вид, а не создавать "похожий, но другой" интерфейс на свободных Tailwind-классах.

### Что переносить пиксель-в-пиксель

| Параметр | Источник | Как реализовать |
|---|---|---|
| Цвета | CSS-переменные `--md-sys-color-*` | `static-prototype-spec.md` §5.1, без изменений значений |
| Типографика | `--font-sans: "Roboto", …` | Тот же шрифт через `next/font` |
| Отступы/радиусы | `--radius-md`/`--radius-lg`, текущие Tailwind-утилиты | Как в прототипе, не заново придуманные значения |
| Структура/порядок блоков | `index.html` (app bar → drawer → main) | Тот же порядок секций на Next.js-странице |
| Брейкпоинты | §4 `static-prototype-spec.md` | Тот же mobile-first подход, без добавления `xl`/`2xl`-тиров, которых не было в прототипе |

### Как проверять при реализации

1. Держать текущий прототип запущенным (`npm run serve`, порт 3000) рядом с Next.js dev-сервером для визуального сравнения при переносе конкретного экрана.
2. Сверять итоговый DOM/классы с §5–§8 `static-prototype-spec.md`, не «по памяти».
3. Реализовывать через shared-компоненты (`components/`), не одноразовые стили на конкретном маршруте.

### Исключения

- Если `nextjs-migration-spec.md`/контракт явно требует иного (например, shadcn `Sheet` вместо самодельного drawer-фокус-трапа) — побеждает более высокий по приоритету документ (см. `data-routing-security.md` §8), не буквальная HTML-структура старого прототипа.
- Реальное расхождение — задокументировать в соответствующей спеке/задаче, не оставлять «известным дрейфом» без записи.
