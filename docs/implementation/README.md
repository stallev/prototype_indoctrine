# Фазы имплементации — Next.js миграция

Живой трекер выполнения Фазы 9 (миграция на Next.js). В отличие от `docs/implementation-checklist.md` (архив Фаз 0–8, статичен, уже принят), файлы в этом каталоге **редактируются агентами пайплайна** (`implementer`/`quality-checker`/`code-reviewer`) по ходу выполнения — статус, попытки и заметки каждой задачи обновляются в файле, а не только в чате.

Пайплайн полностью автономен: пользователь запускает его один раз, дальше все задачи всех файлов ниже (9.1 → 9.5) выполняются без запроса подтверждений, с автоматическим коммитом после каждой успешно проверенной фазы (см. `../multi-agent-workflow.md` §5а, §9) и автопереходом к следующей. `git push` пайплайн не выполняет никогда — это делает пользователь вручную.

**Статус:** предложено (ожидает утверждения)

## 2. Формат задачи

Каждая задача — отдельный подраздел с полями:

```
### 9.N.M — <короткое имя задачи>

- **Статус:** todo | in-progress | blocked | done
- **Попытки:** <число>
- **Definition of Done:** <машинно проверяемый критерий>
- **Описание:** <что именно реализовать, какие файлы затронуты, на что порт/спека>
- **Конвенции:** <ссылки на конкретные файлы/разделы `../conventions/*.md`, применимые именно к этой задаче — не общая ссылка на `coding-conventions.md` целиком>
- **Заметки агентов:** <лог попыток — что менял implementer, что нашёл quality-checker/code-reviewer>
```

Поле `Конвенции` обязательно для задач, создающих/меняющих код (не для чисто административных, как 9.5.3) — `implementer` и `code-reviewer` сверяются именно с перечисленными там разделами, а не ищут применимое по всему `docs/conventions/` заново на каждой задаче.

## 3. Формат фазы

Каждый файл `phase-9.N-*.md` в шапке несёт собственный статус, отдельный от статусов задач внутри:

```
**Статус фазы:** todo | in-progress | in-review | done | blocked
```

- `todo` — ни одна задача фазы ещё не взята.
- `in-progress` — хотя бы одна задача в работе, не все `done`.
- `in-review` — все задачи фазы `done`, идёт фазовый контроль (`multi-agent-workflow.md` §5а: `quality-checker` + `code-reviewer` над всей фазой целиком).
- `done` — фазовый контроль пройден, коммит сделан, пайплайн уже перешёл к следующей фазе.
- `blocked` — фазовый контроль провален 3 раза подряд; коммита нет, пайплайн остановлен, нужна ручная эскалация.

## 4. Кто и как редактирует

- Ведущая сессия пайплайна (`/next-task`) — при взятии задачи выставляет ей `Статус: in-progress`; когда все задачи файла фазы `done`, выставляет фазе `Статус фазы: in-review` и запускает фазовый контроль; по его итогу — `Статус фазы: done` (+ коммит) или `blocked`.
- `implementer` — по завершении попытки добавляет запись в `Заметки агентов` задачи; сам поля `Статус`/`Попытки` не редактирует.
- `quality-checker`/`code-reviewer` — дописывают в `Заметки агентов` (задачи — на обычной стадии, файла фазы в целом — на фазовом контроле) результат проверки (pass/fail + причина); не меняют `Статус` напрямую.
- Ведущая сессия увеличивает `Попытки` задачи после каждого цикла и выставляет `Статус: done`/`blocked` по итогам трёх стадий (см. `multi-agent-workflow.md` §6).
- Пустая задача (не взятая ни разу) остаётся `Статус: todo`, `Попытки: 0`, `Заметки агентов: —`.

## 5. Прогресс

Суммарный статус — по факту чтения `Статус фазы:`/`Статус:` полей во всех файлах фаз; отдельный числовой счётчик здесь не дублируется, чтобы не рассинхронизироваться с реальными полями задач.
